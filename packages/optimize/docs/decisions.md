# decisions — dsh-optimize

> この文書が答える問い: **なぜその設計・技術を選んだか**。現在の設計判断と、採用しなかった代替案、そのトレードオフを記録する。構造の説明は `architecture.md`、要求は `spec.md` を参照する。

## D1 Host half と Client half を1パッケージに同居させる

**決定**: `src/index.ts`（Node）と `src/client.ts`（ブラウザ）の2エントリ構成にする。

**代替案**: クライアントのみのプラグイン、2パッケージ分割。

**理由**: DSH は Host Loader のエントリが読み込んだパッケージのマニフェストから `dsh.client` を読み、
クライアントバンドルを配信する。Host 行が無いとバンドルは配信されないため、クライアントのみは成立しない。
設定値を DSH の設定ドキュメントに載せるにも Host 側の `Config` スキーマが必要になる。
2パッケージ分割は、同一機能の Host/Client が常に同じバージョンで入る保証を失う。

**影響**: ビルドは2エントリ、公開物は `./` と `./client` の2口になる。

## D2 設定は DSH の設定フォームに乗せ、独自ストレージを作らない

**決定**: `Config` の volatile フィールドを唯一の保存先とし、クライアントは `ctx.configForms` で読み書きする。

**代替案**: `localStorage`、プラグイン独自の JSON ファイル、専用 HTTP ルート。

**理由**: DSH の設定フォームは profile の設定ドキュメントへの永続化、revision による競合検出、
volatile フィールドの実行中反映を既に提供する。独自実装はこれらを再実装することになり、
利用者から見て「他の設定と同じ場所に保存されない」不整合を生む。専用ルートは認証・所有権・
エラー処理の面で余計な公開境界を増やす。

**影響**: 設定は `optimize` 名前空間として profile の設定ファイルに現れる。
フィールドは必ず `.volatile()` を付け、ネストした辞書は使わない（単一フィールド書き込みが
名前空間直下のスカラーを前提にするため）。

## D3 1機能 = 1 cordis プラグイン

**決定**: 機能実装を cordis プラグインとし、ON で `ctx.plugin()`、OFF で `Fiber.dispose()` する。

**代替案**: 各機能が `apply` と `dispose` を返す自作インターフェース、常時登録して設定値で `null` を返す方式。

**理由**: cordis の fiber が `inject` による依存待ちと、`ctx.effect` で登録した副作用の逆順解除を担う。
機能ごとの失敗は fiber 単位で隔離され、他機能に波及しない。常時登録方式は再登録の揺れを避けられるが、
OFF の機能もスロットとスタイルの登録を占有し続けるため「OFF は効果が一切ない」という契約を満たせない。
自作インターフェースは同じ後始末の規律を手で守る必要があり、解除漏れが起きやすい。

**影響**: 機能の副作用は `ctx.effect` の中で登録することが必須になる。トグル操作ごとに slot 登録が
付け外しされるが、`register` の disposer は冪等で、再描画は購読経由で行われるため問題にならない。

## D4 CSS は安定した識別子のみに依存する

**決定**: `data-slot="<slot 名>"`、シェルが公開する `data-*` 属性、`--dsw-*` / `--dsh-*` 変数、
`ctx.theme.overrideTokens` だけを使う。`single` スロットの奪取はしない。

**代替案**: CSS Modules のクラス名を直接対象にする、`single` スロットを自前実装で置き換える。

**理由**: スロットはセル単位で合成され、最小 `priority` の生存エントリだけが描画される。出荷側は既定の
`priority: 0` で登録しており、同じセルへ同じ `priority` で登録すると例外になる。子スロットを宣言している席を
奪うと子 UI が描画されず、子席の再宣言も例外になるため、置換は「他プラグインの UI を壊す」危険が高い。
クラス名はビルドごとのハッシュ（例 `_card_u7vgf_24`）で、DSH 更新のたびに変わる。
`data-slot` と `data-*` 属性、CSS 変数は出荷側が自ら使っている安定した識別子で、複数プラグインが同居できる。

**影響**: 既存 UI の「削除」「置き換え」に類する変更はこのプラグインの範囲外になる。
単純な追加（`list` / `keyed` への寄与）と、CSS・テーマトークンによる見た目の調整を優先する。
将来 `single` を使う場合は、子席を持たない席に限り負の `priority` で登録する。

## D5 既定値はすべて OFF

**決定**: 機能は明示的に有効化したときだけ効果を持つ。

**代替案**: 便利な機能を既定 ON にする。

**理由**: プラグイン導入が GUI の見た目・挙動を暗黙に変えると、原因の特定が難しく、
DSH 本体の更新との切り分けもできなくなる。OFF 既定なら、導入時点の挙動は変わらない。

**影響**: 導入直後はタブに機能一覧が出るだけで、見た目は変わらない。

## D6 設定タブはトップレベルのセクションにする

**決定**: `settings.section` を使い、`id: optimize`、`order: 25`、`label: "Optimization"` で登録する。

**代替案**: Settings の Plugins セクション内のタブ（`settings.plugins.tab`）、General の行（`settings.general.item`）。

**理由**: 機能数が多く、一覧・検索・一括操作を持つ独立ページが必要になる。`settings.general.item` は
1設定1行のための席で、多数のトグルを置く場所ではない。`settings.plugins.tab` は
プラグイン設定の置き場としては自然だが、機能一覧を探す導線としては奥すぎる。

**影響**: 設定ナビゲーションの項目が1つ増える。`order` は出荷セクションの並び（-10〜20）の直後の `25` に置く。

## D7 UI 部品は `dsh-client-ui-primitives` を使う

**決定**: `Switch`、アイコンなど、シェルがモジュール表で公開している primitives を使う。

**代替案**: 素の HTML 要素と自前 CSS（既存プラグインの siwc が採用している方式）。

**理由**: 見た目・フォーカス・キーボード操作を DSH 本体と揃えられる。primitives はシェルの
モジュール表に含まれ、クライアントバンドルから `require` できる。`Switch` は
`checked` / `onChange` / `label` / `disabled` を持つ制御コンポーネントで、即時保存のトグルにそのまま使える。

**影響**: devDependency として primitives を追加し、バージョンは動作確認済みの DSH に合わせる。
primitives はシェルの共有モジュール表（`PLATFORM_MODULES`）に含まれるため、`dsh.client.external` には
宣言しない（external はベースライン外の要求だけを書く）。peerDependency にも置かない
（`@deepseek-ai/dsh-*` 名の peer は DSH 本体のバージョン要件として評価され、意図しない互換ゲートになる）。
シェルのモジュール表から消えた場合はページの描画が失敗するため、`development.md` の追従手順で確認する。

## D8 設定ページは tsx で書く

**決定**: `src/page` と `src/features` の UI は `.tsx` と automatic runtime で書く。

**代替案**: `createElement` の手書き（siwc の方式）。

**理由**: 機能一覧、検索、一括操作、行のバリエーションを持つページは要素ツリーが深く、
`createElement` では可読性が落ちる。automatic runtime は `react/jsx-runtime` を
モジュール表から `require` する形に変換できる。

**影響**: tsconfig で `jsx: react-jsx` を有効にし、ビルド成果物に生の JSX が残っていないことを
`verification.md` の I8 で検査する。

## D9 表示言語は英語のみ

**決定**: 設定タブの文言は英語リテラルで持つ。`ctx.locale` は使わない。

**代替案**: 日本語併記、locale サービスへの辞書登録。

**理由**: locale サービスの型付き登録は複数の基盤言語辞書を要求し、辞書の管理コストが
小さな設定ページに対して過剰になる。表示を1言語に固定すれば、文言の欠落検出も単純になる。

**影響**: 非英語環境でも本プラグインの文言は英語で表示される。`locale/*.json` は
プラグイン一覧カード用のメタ情報のみを持つ。

## D10 当面は `file:` インストールで運用する

**決定**: npm 公開とタグリリースは行わず、ローカルパスから profile にインストールする。

**代替案**: 最初から npm 公開、Git リポジトリ指定。

**理由**: 機能セットが固まるまで API と設定キーが変わる。公開すると互換性維持の責務が先に発生する。

**影響**: 利用は開発者のローカル環境に限られる。公開する場合は
`package.json` の `files` と Release ワークフローの対象を追加する作業が別途必要になる。

## D11 バージョン要件は peerDependencies のリテラルで表す

**決定**: `peerDependencies` に `@deepseek-ai/dsh-*` を `^0.2.1-rc.2` のリテラルで並べ、
`engines.dsh` は宣言しない。起動時は `EXPECTED_DSH_VERSIONS` に無いバージョンなら警告だけ残す。

**代替案**: `engines.dsh` で範囲を厳格に宣言して不一致なら起動させない、peer を省略する。

**理由**: DSH の互換判定は `engines.dsh` があればそれだけで決まり、無ければ `@deepseek-ai/dsh*` の
peer すべてを prerelease 込みで判定する。`^0.2.1-rc.2` は検証済みの実行バージョン（0.2.2-alpha.3）を
含み、型検査に使う版を下限にできる。`engines.dsh` で固定すると、検証していない将来の版を
利用者の環境から締め出すことになる。本プラグインはプライベートな `file:` 配布なので、
互換性の最終判断は利用者の環境で行うのが現実的。

**影響**: 未検証の DSH でもインストール・起動できる。壊れた場合の切り分けは `EXPECTED_DSH_VERSIONS` と
起動ログで行う。`pnpm-workspace.yaml` のカタログは `catalog:` 記法のまま使えるが、peer は catalog 不可。

## D12 UI に限定せず、Host 側の振る舞いも機能として扱う

**決定**: 機能は Host 面・Client 面・その両方のいずれでも実装できる。設定タブと設定キーは面によらず1つ。

**代替案**: UI 専用プラグインに限定する。Host 用と Client 用でプラグインを分割する。

**理由**: 利用者から見ると「見た目を変える」と「振る舞いを変える」は同じ作業で、探す場所が分かれると
使いにくい。プラグインを分割すると、設定タブと設定キーの一覧が2つに増え、同じ設定機構を二重に持つ。
1機能 = 1トグルというモデルは作用する面に依存しないので、同じレジストリで扱える。

**影響**: Host 側の機能には、再起動しないと反映できないものが生じる。即時反映できるものだけを即時反映し、
残りは `reload: "restart"` として設定ページに明示する。Host と Client の実装マップは別ファイルにする
（Host バンドルに React を巻き込まないため）。

## D13 Host 側の即時反映は `loader/volatile-update` の購読で行う

**決定**: Host ランタイムは `ctx.on("loader/volatile-update", ...)` を購読し、値の変化後に差分適用する。

**代替案**: `settings/document-updated` の購読、非 volatile フィールドによる fiber 再マウント、再起動必須のみ。

**理由**: 設定フォームに出すには `.volatile()` が必須で、volatile フィールドの変更は
プラグインを再マウントしない（Loader が参照値だけを差し替える）。`settings/document-updated` は
`describe()` が実行されたときにだけ emit されるため、書き込み経路に依存する。
`loader/volatile-update` は所有 fiber に、値が実際に変わったときだけ配送され、通知時点で新しい値は
commit 済みなので、通知を受けてから `config.<id>.get()` を読めばよい。非 volatile フィールドは
設定フォームから編集できないため、再マウント方式は選択肢にならない。

**影響**: `@deepseek-ai/cordis-plugin-loader` の型宣言に依存する。Loader を経由しない変更
（profile の YAML を直接編集するなど）は次回起動まで反映されない。

## D14 機能0件でも設定タブを出すため、内部フィールド `schemaVersion` を持つ

**決定**: 生成する設定スキーマに、機能とは別の volatile フィールド `schemaVersion`（既定値 1）を常に含める。

**代替案**: 機能が1件も無い間は設定タブを出さない、スキーマのルートを volatile にする、機能0件のときだけダミー機能を登録する。

**理由**: `settings.describe()` は volatile フィールドを1つも持たない名前空間を配信対象から外すため、
機能0件のフラットなスキーマでは `whileServed(["optimize"])` が発火せず、設定タブが登録されない。
機能が追加されるまでの暫定ではなく、`schemaVersion` は将来キーを移行するときの設定ドキュメント互換
バージョンとしても使える。ルートを volatile にすると `config` が `Volatile<...>` になり、
`config.<featureId>.get()` というフィールド単位の読み取りができなくなる。ダミー機能は「機能」の一覧に
偽物を混ぜることになり、契約（S2）と実装マップの整合性テストを壊す。

**影響**: 設定スキーマは「機能のフィールド + `schemaVersion`」になる。`schemaVersion` は設定ページに
描画せず、機能トグルとしても扱わない。フィールド単位の書き込み（`form.set(id, boolean)`）は機能フィールドに
対して従来どおり動く。

## D15 ナビゲーションアイコンは当面シェル既定の glyph に任せる

**決定**: `settings.section.icon` を登録せず、シェルが表示する既定のアイコン（gear）を使う。

**代替案**: 型基準を DSH 0.2.2 系に上げて `settings.section.icon` を登録する、独自アイコンを登録するために
型定義を module augmentation で補う。

**理由**: `settings.section.icon` は DSH 0.2.2 系で追加されたスロットで、ワークスペースの型基準である
0.2.1-rc.2 の `SlotMap` には存在しない。未宣言のスロットへの `register()` は実行時に例外になり、
スロット契約を型で偽装することにもなる。契約 S1 が要求する「アイコンが表示される」はシェル既定の
glyph で満たされる。型基準を 0.2.2 系へ上げる作業は DSH 全体の依存更新として別に行う。

**影響**: 設定ナビゲーションのアイコンは他セクションの既定 glyph と同じ見た目になる。DSH の型基準を
上げた時点で `settings.section.icon` の登録を追加できる。
